# LEVEL 选择协议

## 何时读取

项目首次进入流程、范围显著变化、责任模式变化、风险升级或用户质疑当前 LEVEL 时读取。LEVEL 先判断责任模式，再叠加当前动作的 R1–R4 风险。

## 核心区别：持续更新与持续运营

持续更新只表示交付物可以重新打包、上传或发布新版本；持续运营表示项目负责人要长期承担线上可用性、用户/权限、云端数据、服务端逻辑、备份、回滚、监控、反馈或支持责任。前者不单独触发 LEVEL 2，后者通常触发 LEVEL 2。

## 判断顺序

| 维度 | LEVEL 1 | LEVEL 2 | LEVEL 3 | LEVEL 4 |
| --- | --- | --- | --- | --- |
| 项目来源 | 独立小项目、离线或静态交付物 | 自己负责的线上项目 | 他人、团队、公司或开源仓库 | 尚未确定实现边界的复杂项目 |
| 责任 | 快速开发、完整项目记忆、下载更新 | 持续在线、完整 PVS 和运营 | 遵守已有仓库、维护者和贡献流程 | 先分析、确认后实施、外部能力路由 |
| 状态与数据 | 无用户账户、云端业务状态或生产数据 | 用户、权限、云端数据、API、任务或线上依赖 | 继承已有仓库的数据和发布责任 | 只做分析，不创建实现状态 |
| 文档底座 | 稳定认知 + Ledger/小记录 | 完整包内 PVS | 既有事实 + 轻量 Change Record | 分析材料、十节点参考和路由记录 |
| 验证节奏 | 完成/打包前集中冒烟和人工验收 | 按风险、集成、里程碑和版本集中安排 | 修改前基线、复现、受影响回归、CI、Review | 需求验收标准和风险分析 |

## 推荐规则

使用 LEVEL 3：项目属于他人、团队、公司或开源仓库，需要遵守已有规则、贡献、CI、Review、PR 或交接流程。

使用 LEVEL 2：项目由自己负责，需要上线并持续运营，承担用户系统、云端状态、生产数据、服务端逻辑、公开 API、定时任务、监控、备份、回滚、反馈或支持责任。

使用 LEVEL 1：项目是离线工具、命令行工具、脚本、Skill、插件、游戏 Mod、原型 Demo、静态页面、展示页、活动页或没有用户系统的静态 Web 工具；也包括可以重新打包并供用户下载、但没有持续在线服务责任的项目。

使用 LEVEL 4：项目是大型产品、多系统编排、复杂自动化、多人协作或完整运营自动化；先完成需求和方案，负责人确认后按参考节点实施。

“以后可能更新”“可以部署到静态托管”“会重新上传下载包”都不能单独把项目升级到 LEVEL 2、3 或 4。

## 选择优先级

同时满足多个条件时按责任更明确的路径选择：

1. 他人/团队/开源项目优先 LEVEL 3。
2. 复杂、多系统项目优先 LEVEL 4；先分析并确认实现边界。
3. 自有中小型线上产品使用 LEVEL 2。
4. 只有静态、离线或可下载交付物使用 LEVEL 1。
5. 高风险动作另外按 R1–R4 设置人工 Gate，不能用 LEVEL 替代风险确认。

## 边界示例

| 场景 | 推荐 | 负例边界 |
| --- | --- | --- |
| 可下载新版本的离线工具 | LEVEL 1 | 若增加云端账号、在线数据或持续在线服务，改评 LEVEL 2 |
| 部署到线上但没有用户系统的静态页面 | LEVEL 1 | 若承担服务端状态、公开 API 或长期在线支持，改评 LEVEL 2 |
| 有登录、云端数据和持续发布责任的自有产品 | LEVEL 2 | 若只是向他人仓库提 PR，改评 LEVEL 3 |
| 参与 GitHub 开源仓库或团队已有项目 | LEVEL 3 | 即使只改一个文件，也保留基线和回归责任 |
| 多系统复杂自动化或大型产品 | LEVEL 4 | 先分析；负责人确认后可实施并路由外部能力 |

## 人工确认

输出推荐、事实、假设、责任依据和改用其他 LEVEL 的影响。用户明确确认前不初始化正式流程。无法区分时推荐责任更高且边界更明确的等级，并说明降级需要确认哪些事实。
