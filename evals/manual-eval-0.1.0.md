## 评测方法

逐条按 `SKILL.md` 的触发检查与 `references/level-selection.md` 的判定规则执行路由，只观察触发、推荐 LEVEL、读取范围和停止位置。评测不创建项目文件，不执行 Git 或远端动作，也不把预期结果当作实际平台集成测试。

## 场景 1：静态网页小工具

提示：帮我做一个不需要数据库的静态网页小工具，先判断 LEVEL 并推进到下一个人工 Gate。

- 观察结果：触发 `project-level-workflow`。
- 推荐：LEVEL 1。
- 原因：单一核心路径、无数据库、短生命周期、最终统一测试与宣传。
- 停止位置：首次 LEVEL 确认 Gate；确认前不读取其他 LEVEL SOP，不创建实现文件。
- 结果：通过。

## 场景 2：已有 GitHub 项目 Bug

提示：帮我修复这个已有 GitHub 项目的一个 Bug，先理解仓库再推进。

- 观察结果：触发 `project-level-workflow`。
- 推荐：LEVEL 2。
- 原因：工作对象是已有仓库，目标是局部修复，并需要项目地图、影响范围和回归验证。
- 停止位置：首次 LEVEL 确认 Gate；确认前不修改仓库，不初始化 Git，不创建远端内容。
- 结果：通过。

## 场景 3：长期运营 SaaS

提示：我要开发一个长期运营的 SaaS，请按严格流程从调研开始。

- 观察结果：触发 `project-level-workflow`。
- 推荐：LEVEL 3。
- 原因：长期运营、数据库与账号体系、可靠性、监控、回滚和持续维护要求高。
- 停止位置：首次 LEVEL 确认 Gate；确认前不直接进入设计、开发或技术栈选择。
- 结果：通过。

## 结论与限制

三条提示分别稳定路由到 LEVEL 1、2、3，并都停在首次人工 Gate。该结果验证了文档规则的一致性；Codex、Claude Code 与 Cursor 的真实触发率仍需在各平台安装后继续采样。
