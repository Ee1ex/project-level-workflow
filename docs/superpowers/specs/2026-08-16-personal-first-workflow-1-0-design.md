# Project Level Workflow 1.0 个人开发优先设计

状态：用户已于 2026-08-16 明确批准。

## 目标

把 Project Level Workflow 从“所有项目共享同一套风险与 Gate 密度”调整为双轨分层：LEVEL 1–3 使用以项目记忆和可追溯为核心的个人开发流程；LEVEL 4 保留复杂自动化项目参考、显式风险与外部能力路由。发布版本改为两段式 `X.X`，本次为 `1.0`。

## 依据

- PVS 文章：<https://ai.codefather.cn/post/2082394818868260866>
- AI 项目自动化流水线文章：<https://ai.codefather.cn/post/2075533184434438146>
- 包内 PVS：`core/project-vibe-spec/PVS.md`，同步来源提交 `dae5315`
- 当前发布基线：GitHub `v0.4.0`

第一篇文章和包内 PVS 提供共同地基：`AGENTS.md`、文档治理、范围冻结、Phase、DoD、变更可追溯和跨 Agent 接管。第二篇文章的六层架构、十节点、显式风险、自动化、Inbox、MCP 权限和复盘只在 LEVEL 4 保留为参考流程。

## 优先级

1. LEVEL 1：个人快速开发，最高优先级。
2. LEVEL 2：个人持续运营项目，最高优先级。
3. LEVEL 3：已有、团队和开源项目改进，次优先级。
4. LEVEL 4：复杂项目与自动化交付参考，非主要个人使用路径。

## 共同不变量

- 所有 LEVEL 都必须先由项目负责人显式确认，尤其 LEVEL 1 不允许软确认后直接写入。
- 先读取项目规则、现有事实和 Git 状态，不建立平行事实源。
- 明确目标、核心路径、范围、不做项和完成定义。
- 采用可验证切片推进；未运行检查只能记录为待验证。
- 持久化项目从 0 到 1 的结构、演进、决策、验证和版本历史。
- 批量删除、生产数据、密钥、支付、账号权限、不可逆迁移、生产发布、公开发布、Merge、Release 和对外发送保留人工确认。
- Force Push 和改写公共历史继续禁止。
- 包内仍只有根 `SKILL.md` 一个可发现 Skill；PVS 继续内嵌且离线可用。

## 双层文档契约

### 稳定认知层

回答“项目现在是什么”，至少覆盖：

- `AGENTS.md`：行为规则、事实优先级、禁止事项和入口。
- `DOCUMENT_MAP.md`：唯一文档导航。
- 项目目标、用户、核心路径、范围和不做项。
- 当前架构、目录、模块关系、数据和外部依赖。
- 当前状态、已知限制、构建、测试、打包和交付方式。

### 演进记录层

回答“项目为什么变成现在这样”，使用 PVS 现有命名体系：

- `Requirements/LEDGER.md` 与 `REQ-*`。
- `Decisions/LEDGER.md` 与 `DEC-*`。
- `Progress/LEDGER.md` 与 `PROG-*`。
- Bug 记录、`CHANGELOG.md`、Release Record 和验证证据。

记录粒度：

| 变化 | 最小记录 |
| --- | --- |
| 文案、样式、小配置 | Progress Ledger/Changelog 一条结构化记录 |
| 小功能、小 Bug | 轻量 Change Record：目标、范围、文件、行为、验证、兼容影响 |
| 跨模块功能 | REQ + PROG；有取舍时增加 DEC |
| 架构、数据、权限变化 | 详细 REQ + DEC + 更新稳定认知层 |
| 正式版本 | CHANGELOG + 不可变 Release Record |

大文档不为每个小切片复制；小记录必须链接受影响的大文档和实际验证。新增/删除模块、调用关系、持久化、构建交付、核心路径或范围变化时必须回写稳定认知层。

## LEVEL 1：快速开发与完整项目记忆

适用离线工具、Skill、插件、脚本、CLI、静态页面、原型、Demo、Mod 和可下载交付物。

流程：

```text
发现项目 → 推荐 LEVEL 1 → 用户显式确认 → 初始化项目记忆
→ 冻结当前版本范围 → 实现—运行—观察—调整
→ 持续记录大小变更 → 集中验收 → GitHub 交付
```

默认生成或复用稳定认知层、Requirements/Decisions/Progress Ledger、状态和待验证记录。小改动追加小记录，不强制完整方案、显式 R1/R2 或阶段 Gate。

LEVEL 1 Gate 仅包括 LEVEL 确认、实质范围/方向改变、硬性安全边界和远程发布。

## LEVEL 2：完整 PVS 持续运营

适用个人负责且承担账号、权限、云端数据、服务端、部署、备份、回滚、监控或用户支持责任的产品。

确认后自动进入 Phase 0，并全量采用 PVS：

- `AGENTS.md`、`DOCUMENT_MAP.md`。
- PDD、PRD、Requirements、Decisions、Progress。
- 业务流、UI/交互、架构、API、数据、权限、失败路径。
- 部署、环境、监控、备份、回滚、运营、Bug、待验证和版本历史。
- 范围冻结和 Phase 0 → Phase N，每个 Phase 有目标、前置、范围、交付物、DoD、验证、文档同步和下一阶段。

Phase 完成不是人工 Gate。只要范围未变、DoD 满足且未触发硬性边界，Agent 可自动推进。Gate 仅用于产品/技术多方案、架构、数据语义、认证权限、安全、公共兼容性、支付、生产和 Release。

## LEVEL 3：已有仓库改进

流程：读取规则 → 项目地图/受影响基线 → 复现或确认需求 → 最小兼容修改 → 受影响回归 → 文档与变更记录 → PR/交接。

优先复用 Issue、PR、CHANGELOG、ADR 和现有文档。仓库缺少接管入口时补轻量 Project Map；每次修改保留 Change Record。小变更不铺设完整 PVS 目录，跨模块变更必须更新架构、接口或贡献文档。

## LEVEL 4：复杂自动化参考与路由

LEVEL 4 从“永久只分析”改为“先分析，负责人确认后可实施”，但主包不内置十个专业 Skill。

参考节点：需求判断、原型、技术方案、任务拆解、实现、测试联调、代码审查、部署准备、日志排查、复盘。到达节点时检查能力是否已安装；已安装则路由，未安装则报告来源、用途、权限和降级路径，并提醒安装。安装需要用户确认；拒绝安装时使用通用能力并记录缺口。

LEVEL 4 保留显式风险和阶段 Gate，但外部 Skill 不得覆盖本工作流权限。

## 执行策略与 Gate

LEVEL 1–3 对用户只暴露：

- `AUTO`：已确认范围内连续执行。
- `CONFIRM`：缺少用户决策或即将产生高影响。
- `MANUAL_ONLY`：Agent 只准备，不执行。

内部 `risk` 字段为兼容状态可以保留，但不再要求普通任务逐轮报告 R1–R4。Gate 只表示“没有用户决定就不能安全继续”，进度汇报、测试通过、完成普通功能、本地提交都不是 Gate。一次有界授权持续有效，只有范围、事实、风险或外部目标变化才重新确认。

## GitHub 插件路由

所有 LEVEL 进入推送、PR、Merge、Tag 或 Release 任务时自动选择 Codex GitHub 插件：

1. 自动执行仓库、身份、分支、远端和 Release 状态的只读检查。
2. 检查本地 Diff、范围和验证证据。
3. 生成一份合并后的远程动作计划。
4. 在动作发生前取得一次明确确认。
5. 使用 GitHub 插件执行批准的操作。
6. 再读取远端 Commit、PR、Tag、Release 验证结果。
7. 回写 CHANGELOG、Release Record 和状态证据。

插件不可用时说明安装/连接要求，不静默切换为不受治理的写入方式。

## 版本规范

- 本次 `VERSION`、`workflow_version`、evals、Changelog 和 Release 使用 `1.0`。
- Git Tag 使用 `v1.0`。
- 后续兼容增强/修复递增第二段：`1.1`、`1.2`。
- LEVEL 语义、状态协议或核心兼容性重大变化递增第一段：`2.0`。
- 公共版本正则为 `^[0-9]+\.[0-9]+$`，不再称为 SemVer。
- 状态 Schema 升为两段式 `2.0`，与公开工作流版本独立。
- 包和新状态只写两段版本；状态读取与迁移必须兼容历史三段值 `0.4.0`，直到安全刷新为 `1.0`。

## 兼容迁移

- 旧 LEVEL 1–3 保持等级不变，不增加迁移 Gate。
- 旧 LEVEL 4 保持分析阶段；进入新实施阶段必须负责人确认。
- 旧文档和模板不删除，继续作为事实源或兼容入口。
- 更新状态前写 `state.backup.json`，记录从旧 workflow/schema 到 `1.0`/`2.0`。
- 不自动授予 GitHub、生产或外部 Skill 权限。

## 非目标

- 不内嵌 LEVEL 4 的十个外部 Skill。
- 不让所有小修改生成独立大型文档。
- 不自动 Merge、Release、生产发布或安装第三方 Skill。
- 不删除旧模板或用户项目文档。
- 不改变包内 PVS 的来源授权和单 Skill 结构。

## 验收场景

- LEVEL 1 未显式确认前不初始化、不写代码；确认后建立大文档与小记录体系。
- 小修改进入 Progress/Changelog，跨模块修改同时更新稳定认知层。
- 新 Agent 仅靠文档可恢复目标、架构、历史、当前状态和安全边界。
- LEVEL 2 初始化完整 PVS 与 Phase 0，Phase 满足 DoD 后不逐阶段索要批准。
- LEVEL 3 优先复用原仓库事实源并保留轻量 Change Record。
- LEVEL 4 只路由外部 Skill；缺失时提醒安装并支持通用降级。
- 所有 LEVEL 的 GitHub 交付自动选择 GitHub 插件，远程写入前确认并在完成后验证。
- 所有公开版本只接受 `X.X`；`0.4.0` 状态可安全迁移并保留备份。
